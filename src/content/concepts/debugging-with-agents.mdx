Có một bẫy khi debug cùng agent: bạn thấy lần đầu agent không fix được, bạn giải thích thêm. Lần hai vẫn sai, bạn paste thêm error log. Lần ba agent có vẻ tự tin hơn nhưng lỗi mới xuất hiện. Context của phiên giờ đầy lý giải sai + giải pháp thất bại — và agent tiếp tục *xây lên đống đó*. Bạn không đang debug nữa, bạn đang chất đống suy luận lỗi.

## Là gì

**Debugging Decay Index** (2026) đo hiện tượng hiệu quả debug của agent *tụt* 60-80% sau 2-3 lần thử thất bại trong cùng một phiên. Mỗi lần fail, context nhồi thêm error message + giải thích bịa — agent lần sau không bắt đầu từ đầu mà từ *đống lỗi tích lũy*. Càng nhiều lần thử, model càng drift xa nguyên nhân thực.

Quy tắc thực chiến từ đây: **dừng sau 2-3 lần, reset phiên mới với mô tả gọn.**

## Ví dụ thật

Bug: API trả 500 khi gọi `/users/:id` với ID không tồn tại.

**Sai:** Paste stack trace lần 1 → agent sửa null check → còn lỗi → paste log lần 2 → agent thêm try/catch → lỗi khác → lần 3... Sau 5 lần, code thêm 3 tầng defensive wrapper, bug gốc vẫn còn.

**Đúng:**
1. Viết test fail tái hiện đúng bug: `GET /users/99999 nên trả 404, đang trả 500`.
2. Cho agent chạy test, đọc kết quả, fix.
3. Nếu 2-3 lần agent không xong → đóng phiên, mở phiên mới, prompt gọn: *"GET /users/:id với ID không tồn tại trả 500 thay vì 404. File liên quan: `user.controller.ts`, `user.service.ts`. Fix và verify bằng test."*

Test suite là nền tảng: nó cho agent tín hiệu rõ ràng "đúng/sai" thay vì agent đoán từ mô tả.

<Callout title="Cẩn thận">
Đừng nhồi thêm error log vào phiên đang thất bại. Mỗi lần nhồi, agent "học" từ context sai nhiều hơn. Reset sớm hơn bao giờ hết tốt hơn giải thích thêm.
</Callout>

<Callout title="Nhớ nhé">
Luật cứng: **dừng sau 2-3 lần thất bại, reset phiên mới với mô tả gọn + test fail tái hiện bug**. Không reset = cộng thêm entropy, không trừ.
</Callout>
