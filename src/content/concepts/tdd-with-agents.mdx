Nghĩ đến test như một **hợp đồng**: bạn ký trước những gì "đúng" có nghĩa là gì — rồi mới thuê thợ làm. Nếu thợ làm xong mà hợp đồng không xác nhận được, bạn biết ngay. Viết test *sau* khi agent đã code thì hợp đồng ký sau khi thợ xong việc — không còn ràng buộc được gì nữa.

## Là gì

**TDD với agent** (Test-Driven Agentic Development — TDAD) là quy trình viết test *trước* khi cho agent implement, dùng test như ràng buộc để agent không đi lạc. Điểm khác với TDD truyền thống: thứ quan trọng nhất không phải *quy trình* (write test → red → green → refactor), mà là **ngữ cảnh** bạn cấp cho agent.

Nghiên cứu TDAD 2026 cho thấy: cấp cho agent thông tin về *test nào bị ảnh hưởng* bởi thay đổi giảm regression **70%** (từ 6,08% xuống 1,82%). Nhưng nếu chỉ nhồi *chỉ dẫn quy trình* TDD dài dòng vào prompt mà không kèm ngữ cảnh test cụ thể, kết quả *tệ hơn* (lên 9,94%).

Tóm lại: **context hơn instruction**.

## Ví dụ thật

Bạn cần agent thêm chức năng reset mật khẩu. Thay vì prompt "hãy implement reset password", hãy làm thế này:

1. Mở terminal ở thư mục `tests/auth/` — file implementation chưa nằm trong scope của phiên này.
2. Viết test fail: `test_reset_password_sends_email_to_registered_user`.
3. Cấp cho agent: test mới vừa viết + danh sách test hiện có có thể bị ảnh hưởng (`test_login`, `test_token_expiry`).
4. Prompt: "implement để test này pass, không được làm fail các test kia".

Agent có bản đồ rõ ràng về "đúng" và "không được phá". Nó không cần đoán scope.

<Callout title="Mẹo">
Bắt đầu phiên từ thư mục `tests/` để viết test khi file implementation chưa có trong context. Điều này ngăn agent "đọc implementation rồi viết test khớp" — kiểu test vô nghĩa nhất.
</Callout>

<Callout title="Nhớ nhé">
Cấp ngữ cảnh test cụ thể (test nào bị ảnh hưởng) quan trọng hơn ra lệnh agent "hãy theo TDD". Hợp đồng phải rõ trước khi thuê thợ.
</Callout>
