Hãy tưởng tượng bạn thuê một người quan sát ngồi cạnh mỗi user và ghi chép: "14:32 — user bấm nút Mua. 14:33 — user điền địa chỉ. 14:34 — user thoát."

Đó chính xác là việc event tracking làm — nhưng bằng code, không bằng người.

## Là gì

**Event tracking** là kỹ thuật gắn code vào sản phẩm để ghi lại những *hành động có ý nghĩa* của user — mỗi lần click, submit, scroll, hay bất kỳ bước nào bạn muốn đo.

Mỗi event gồm hai phần:
- **Event name** — tên hành động, ví dụ `checkout_started`, `feature_used`, `onboarding_completed`.
- **Properties** — thuộc tính bổ sung ngữ cảnh: `plan: "pro"`, `item_count: 3`, `source: "email_campaign"`.

## Ví dụ thật

Bạn muốn biết tại sao user bỏ checkout. Bạn gắn ba event:

```
checkout_started      { cart_value: 250000, item_count: 2 }
payment_info_entered  { method: "momo" }
checkout_abandoned    { last_step: "shipping_address" }
```

Từ đây bạn thấy: 60% user bỏ ở bước nhập địa chỉ. Không cần đoán — dữ liệu nói thẳng.

**Tracking plan** là tài liệu liệt kê: event nào cần đo, tại sao, property nào đi kèm, và ai chịu trách nhiệm giữ đúng convention. Không có tracking plan, sau 3 tháng bạn sẽ có `Button Clicked`, `button_click`, và `btn_clicked` — ba cái đo cùng một thứ, không thể merge.

<Callout title="Cẩn thận">
Convention đặt tên event phải nhất quán từ ngày đầu. Dùng một trong hai: `Object Action` (ví dụ `Checkout Started`) hoặc `snake_case` (`checkout_started`) — và áp dụng cho toàn bộ team. Đổi convention giữa chừng rất đau: data cũ và data mới không thể so sánh trực tiếp.
</Callout>

<Callout title="Nhớ nhé">
Event = hành động. Property = ngữ cảnh của hành động. Viết tracking plan trước khi gắn code — không phải sau. Dữ liệu thiếu nhất quán không thể sửa ngược về quá khứ.
</Callout>
